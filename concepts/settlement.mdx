Settlement is where a trade's value actually moves. Sails does it through pluggable **settlement providers**: the escrow type decides how funds are locked, who holds which keys, and what it takes to release them. Pick the provider that matches your asset, network, and trust requirements — each escrow discloses its own `custodyModel`.

## Providers

<CardGroup cols={2}>
  <Card title="MOCK" icon="flask">
    **Custody:** none — no real funds. For development and tests only.
  </Card>

  <Card title="MULTISIG" icon="bitcoin">
    **Asset:** BTC. 2-of-3 P2WSH multisig: buyer and seller each hold a key on their own device; the node holds the arbiter key. Any two keys can spend — buyer and seller together, or the arbiter with one party after a dispute ruling.
  </Card>

  <Card title="LIGHTNING_HODL" icon="bolt">
    **Asset:** LN_BTC. Arkade (Ark protocol) VTXO/Taproot escrow — not a classic Lightning hold invoice. Same client-held key split as `MULTISIG`. Testnet/mutinynet today.
  </Card>

  <Card title="SAFE_GUARD_EVM" icon="shield">
    **Asset:** EVM stablecoins. Safe smart account with a transaction guard and ERC-4337: buyer and seller keys client-held, a KMS-held arbiter co-signer. Needs a live EVM RPC and bundler on the node.
  </Card>

  <Card title="WDK_USDT_EVM" icon="coins">
    **Asset:** USDT_ERC20. Tether WDK integration — a **server-custodial reference implementation**: one operator-held seed controls its escrows. Testnet only; not a production custody model.
  </Card>

  <Card title="LIQUID_COVENANT" icon="droplet">
    **Reserved** — not implemented. Creating an escrow with this type is rejected.
  </Card>
</CardGroup>

<Note>
  "Client-held keys" means no single party can move funds alone — not the buyer, not the seller, and not the node. It doesn't mean the node holds no key: its arbiter key is what lets a dispute ruling execute.
</Note>

## Lifecycle

```text
CREATED → FUNDS_LOCKED → PAYMENT_PENDING → COMPLETED
               │                │
               │                └→ DISPUTED → COMPLETED | REFUNDED | SPLIT
               ├→ REFUNDED
               └→ EXPIRED
```

<Steps>
  <Step title="CREATED">
    A party creates the escrow for an agreed trade. For client-held-key providers, buyer and seller each submit an escrow public key; the deposit address appears once both are in.
  </Step>
  <Step title="FUNDS_LOCKED">
    The seller funds the escrow and locks it. For on-chain providers the node checks the funding on-chain first.
  </Step>
  <Step title="PAYMENT_PENDING">
    The buyer pays off-chain (for example PIX) and marks the payment sent. Fiat never passes through the protocol; proof of payment can be recorded with [OpenProof](/api/proof).
  </Step>
  <Step title="COMPLETED">
    The seller releases. Funds go to the buyer's **registered payout address** — never to an address supplied at release time.
  </Step>
</Steps>

<Accordion title="Dispute branch">
  Either party can dispute a locked escrow. An arbiter is assigned; the parties submit evidence; the node may add an advisory automated proposal. Only a `RELEASE`, `REFUND`, or `SPLIT` ruling **signed by the assigned arbiter** executes — the escrow then ends `COMPLETED`, `REFUNDED`, or `SPLIT`. See [Disputes](/guides/disputes).
</Accordion>

## Two release paths

**Direct-call providers** (`MOCK`, `WDK_USDT_EVM`) release in one call:

```typescript
await client.settlement.release(escrow.id);
```

**Client-held-key providers** (`MULTISIG`, `LIGHTNING_HODL`, `SAFE_GUARD_EVM`) run a signing round: the node builds an unsigned transaction, each required signer signs it on their own device, and it's broadcast when the last signature arrives:

```typescript
import { generateEscrowKeypair, signEscrowPsbt } from '@satsails/p2p-trading-sdk';

const escrowKey = generateEscrowKeypair();                       // on the device
await client.settlement.submitKey(escrow.id, escrowKey.publicKeyHex);

// … funded, locked, payment marked sent …

const pending = await client.settlement.initiateRelease(escrow.id);
const signed = signEscrowPsbt(pending.unsignedPsbtBase64, escrowKey.privateKey);
const { complete } = await client.settlement.submitTransactionSignature(escrow.id, signed);
```

Use `signEscrowArkTx()` for `LIGHTNING_HODL` and `signEscrowSafeUserOp()` for `SAFE_GUARD_EVM`.

<Warning>
  Store your escrow private key yourself — the node never receives it. If you lose it before the escrow settles, the funds can only be moved through a dispute and an arbiter's ruling.
</Warning>

## Crash recovery

If a node crashes in the middle of a settlement, a reconciliation process finishes the job from durable state — asking the chain or the provider what actually happened — instead of guessing or paying twice.
