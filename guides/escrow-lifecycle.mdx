Every trade's value moves through an escrow managed by a **settlement provider**. Providers differ in who holds the keys and how funds are released, so choose one knowingly. Each escrow discloses its own model in `custodyModel` (see [Settlement API](/api/settlement#get-an-escrow)).

## State machine

```text
CREATED → FUNDS_LOCKED → PAYMENT_PENDING → COMPLETED
               │                │
               │                └→ DISPUTED → COMPLETED | REFUNDED | SPLIT   (by the arbiter's ruling)
               ├→ REFUNDED
               └→ EXPIRED   (client-held-key providers: timelock passed before payment)
```

| State | Meaning |
|---|---|
| `CREATED` | The escrow exists; no funds are locked yet. |
| `FUNDS_LOCKED` | The seller's asset is locked; the buyer can now pay off-chain. |
| `PAYMENT_PENDING` | The buyer marked the off-chain payment as sent; the seller is confirming. |
| `COMPLETED` | Funds were released to the buyer. |
| `REFUNDED` | Funds were returned to the seller. |
| `SPLIT` | An arbiter split the funds between buyer and seller. |
| `DISPUTED` | A party opened a dispute; funds wait for a ruling. |
| `EXPIRED` | The timelock passed before payment; the seller can recover through arbitration. |

## Providers

| Provider | Custody model | Release | Maturity |
| --- | --- | --- | --- |
| `MOCK` | None — no real funds | Direct | Development and tests only |
| `MULTISIG` | 2-of-3 Bitcoin P2WSH: buyer and seller keys client-held, arbiter key held by the node | Signing round | Real; testnet by default, micro-value mainnet settlement proven |
| `LIGHTNING_HODL` | Arkade (Ark) VTXO/Taproot escrow, same key split as `MULTISIG` | Signing round | Real; testnet/mutinynet |
| `SAFE_GUARD_EVM` | Safe smart account + ERC-4337; buyer and seller keys client-held, KMS-held arbiter co-signer | Signing round | Client-side signing real; needs a live EVM RPC and bundler |
| `WDK_USDT_EVM` | Server-custodial reference implementation (one operator seed) | Direct | Testnet only — not a production custody model |
| `LIQUID_COVENANT` | — | — | Reserved; rejected at creation |

<Warning>
  With the client-held-key providers, **any two of the three keys** can move the funds. Buyer and seller can settle together without the node; the node's arbiter key plus one party's signature is how a disputed escrow is paid out after a ruling. Neither party alone — and not the node alone — can move funds.
</Warning>

If you omit `type` when creating an escrow, the node picks the provider registered for the asset. A node running with mock escrow (the local Docker default) routes every escrow to `MOCK`, whatever type is stored — don't read a successful local run as proof a real provider works.

## Before you trade: payout addresses

Every release, refund, and ruling pays the beneficiary's **registered payout address** for the escrow's asset. Addresses passed at release time are ignored. Register yours first:

```typescript
await client.settlement.setPayoutAddress({ asset: 'BTC', address: 'bc1q…' });
```

## Direct-call providers (MOCK, WDK_USDT_EVM)

```typescript
// Seller
const escrow = await client.settlement.create({ tradeId: trade.id, lockedAmount: '10', asset: 'USDT_ERC20' });
await client.settlement.lock(escrow.id);

// Buyer, after paying off-chain
await buyer.settlement.markPaymentSent(escrow.id);

// Seller, after confirming the payment
await client.settlement.release(escrow.id); // pays the buyer's registered address
```

## Client-held keys (MULTISIG)

Each party generates an escrow keypair on their own device. It's separate from the identity key and must never leave the device.

```typescript
import { generateEscrowKeypair, signEscrowPsbt } from '@satsails/p2p-trading-sdk';

// 1. Each party generates its own escrow key (store privateKey securely).
const escrowKey = generateEscrowKeypair();

// 2. One party creates the escrow.
const escrow = await client.settlement.create({ tradeId: trade.id, lockedAmount: '0.001', asset: 'BTC', type: 'MULTISIG' });

// 3. Buyer and seller each submit their own public key (hex).
await client.settlement.submitKey(escrow.id, escrowKey.publicKeyHex);

// 4. Once both keys are in, the deposit address appears on the escrow.
const { multisigAddr } = await client.settlement.get(escrow.id);
// The seller sends the BTC to multisigAddr on-chain, then:
await client.settlement.lock(escrow.id); // the node verifies the funding before locking

// 5. After the buyer's markPaymentSent(), start a release round.
const pending = await client.settlement.initiateRelease(escrow.id);

// 6. Each required signer signs the PSBT on their own device and submits it.
const signed = signEscrowPsbt(pending.unsignedPsbtBase64, escrowKey.privateKey);
const { complete } = await client.settlement.submitTransactionSignature(escrow.id, signed);
// complete === true once every required signer has submitted: the transaction was broadcast.
```

<Note>
  `multisigAddr` stays `null` until both buyer and seller have submitted their keys. Never fund an escrow before the address exists.
</Note>

Refunds follow the same pattern with `initiateRefund()`. Only one round can be in flight per escrow; read it with `getPendingTransaction()`.

## LIGHTNING_HODL

The flow mirrors `MULTISIG`, but the payload is an Ark transaction bundle and you sign it with the async `signEscrowArkTx()`:

```typescript
import { signEscrowArkTx } from '@satsails/p2p-trading-sdk';

const pending = await client.settlement.initiateRelease(escrow.id);
const signed = await signEscrowArkTx(pending.unsignedPsbtBase64, escrowKey.privateKey);
await client.settlement.submitTransactionSignature(escrow.id, signed);
```

## SAFE_GUARD_EVM

Same round, different payload: a JSON bundle containing an ERC-4337 user operation. Sign its `userOpHash` with `signEscrowSafeUserOp()` and submit the resulting `0x`-prefixed signature through the same `submitTransactionSignature()` call. Final broadcast needs the node to have a bundler configured.

## Two-person approval

Nodes can require both parties to approve a release before it runs (`approveRelease()`, `getReleaseApprovals()`). When the node has this enabled, releases wait until `readyToRelease` is `true`.

## Checking status

```typescript
const escrow = await client.settlement.get(escrowId); // party or assigned arbiter
console.log(escrow.status, escrow.custodyModel, escrow.events);
```

`events` is the escrow's full transition history.

If something goes wrong — the seller doesn't release, or the payment never arrives — open a dispute. See [Disputes](/guides/disputes).
