A Sails deployment is a **node** — the TypeScript reference implementation — that your application talks to over HTTP and WebSocket, usually through the Sails P2P Trading SDK. The node runs the protocol modules on PostgreSQL and Redis, and plugs in external technology where it adds real value: settlement providers for moving assets, Pears for peer-to-peer transport, and QVAC for local AI.

```text
            Your application (wallet, exchange, OTC desk)
                 @satsails/p2p-trading-sdk · @satsails/sdk-react
                                 │  HTTP /v1/*  ·  WebSocket (ticket auth)
┌──────────────────────────── Sails node ─────────────────────────────┐
│ OpenIdentity · OpenLiquidity · OpenP2P · OpenSettlement             │
│ OpenReputation · OpenProof · OpenAgents · Intent Engine             │
│ Capability Registry · settlement reconciliation                     │
│   PostgreSQL (durable state)            Redis (sessions, tickets)   │
└──────┬──────────────────────┬───────────────────────┬───────────────┘
       │                      │                       │
 Settlement providers    Pears / HyperDHT         QVAC (local LLM)
 MULTISIG · LIGHTNING_HODL · optional P2P          intents, risk,
 SAFE_GUARD_EVM · WDK_USDT_EVM  discovery/transport  advisory rulings
       │
 Bitcoin · Ark · EVM chains
```

The protocol itself is a specification of interfaces, events, and behavior. The node is one implementation of it; any implementation that satisfies the contracts is a valid Sails node.

## The external pieces

<CardGroup cols={3}>
  <Card title="Settlement providers" icon="key">
    Move the asset. `MULTISIG` builds 2-of-3 Bitcoin P2WSH escrows with bitcoinjs; `LIGHTNING_HODL` uses Arkade; `SAFE_GUARD_EVM` uses Safe + ERC-4337; `WDK_USDT_EVM` uses Tether's **WDK** for real USDT transfers as a server-custodial reference implementation.
  </Card>

  <Card title="Pears" icon="network-wired">
    Holepunch's HyperDHT gives each participant an optional P2P node (`/v1/peers`) for peer discovery, per-trade topics, and direct offer broadcast — alongside, not instead of, the node's HTTP and WebSocket APIs.
  </Card>

  <Card title="QVAC" icon="microchip-ai">
    Tether's local AI runtime (llama.cpp) on the node. It drafts intents and offers, assesses intent risk, flags social-engineering patterns in chat, and can propose advisory dispute rulings. No cloud AI service.
  </Card>
</CardGroup>

## Nine protocol primitives

<AccordionGroup>
  <Accordion title="1. Identity — who is participating">
    An Ed25519 keypair, registered on a node with proof of possession, authenticated by signing challenges. No email, username, or password.

    **API:** `POST /v1/identity/register-challenge`, `POST /v1/identity/participants`, `POST /v1/identity/challenge`, `POST /v1/identity/authenticate`
  </Accordion>

  <Accordion title="2. Intent — what someone wants">
    A validated declaration of a desired outcome. `TradeIntent` is implemented today; the Intent Engine runs it through `CREATED → VALIDATED → COORDINATED` and can find a matching offer within its declared limits.

    **API:** `POST /v1/intents`, `POST /v1/intents/:id/propose`, `DELETE /v1/intents/:id`
  </Accordion>

  <Accordion title="3. Discovery — who else">
    Offers live in the node's offer book (OpenLiquidity), searchable by asset, side, payment method, and price. Participants can also broadcast offers to connected peers over HyperDHT.

    **API:** `POST /v1/liquidity/offers`, `GET /v1/liquidity/offers`, `POST /v1/liquidity/match`
  </Accordion>

  <Accordion title="4. Negotiation — how terms get agreed">
    Each trade has a real-time channel (chat, status, escrow, presence, and risk events) relayed and stored by the node, with catch-up after disconnections. Structured, agent-to-agent negotiation is designed but not implemented.

    **API:** `WS /v1/openp2p/chat?ticket=…`, `GET /v1/openp2p/chat/:tradeId/messages`, `POST /v1/openp2p/trades/:id/reconcile`
  </Accordion>

  <Accordion title="5. Settlement — how value moves">
    Behind the `SettlementProvider` interface: `MOCK`, `MULTISIG`, `LIGHTNING_HODL`, `SAFE_GUARD_EVM`, and `WDK_USDT_EVM` (`LIQUID_COVENANT` reserved). Client-held-key providers release through signing rounds; a reconciliation process finishes settlements interrupted by a crash from durable state.

    **API:** `POST /v1/settlement/escrow`, `…/lock`, `…/initiate-release`, `…/submit-transaction-signature`, `…/release`
  </Accordion>

  <Accordion title="6. Reputation — why to trust">
    An outcome-based score tied to the identity; only settlement outcomes move it. Ratings are informational; vouches put the voucher's own score at stake.

    **API:** `GET /v1/reputation/:participantId`, `POST /v1/reputation/rate`, `POST /v1/reputation/vouch`
  </Accordion>

  <Accordion title="7. Agent — who assists">
    Local AI drafts and advises; it never signs, negotiates, or moves funds. Social-engineering detection only raises warnings.

    **API:** `POST /v1/agents/generate-trade-intent`, `POST /v1/agents/generate-offer-intent`, `POST /v1/agents/assess-intent-risk`
  </Accordion>

  <Accordion title="8. Proof — how a claim is verified">
    The `Claim → Proof → Verification` chain, with signed evidence media (local or S3-compatible storage), duplicate-evidence detection across trades, optional OpenTimestamps anchoring, and hash-chained trade evidence bundles.

    **API:** `POST /v1/proof/claims`, `POST /v1/proof/proofs`, `POST /v1/proof/proofs/:id/evidence`, `GET /v1/proof/trades/:tradeId/bundle`
  </Accordion>

  <Accordion title="9. Dispute — how disagreements resolve">
    An assigned arbiter reviews evidence and issues a ruling signed with their own key; the node verifies it before settling. QVAC may add an advisory proposal that either party can contest; it never executes on its own. Appeals are available under market arbitration.

    **API:** `POST /v1/settlement/escrow/:id/dispute`, `POST /v1/settlement/disputes/:id/resolve`
  </Accordion>
</AccordionGroup>

Two Core components work across the primitives without being primitives themselves: the **Capability Registry** (a participant's recorded consent to gated actions, enforced on production nodes) and the **Policy Engine** (rules that govern how primitives behave).

## Assets

Offers and intents accept these assets: `BTC`, `LN_BTC`, `LIQUID_BTC`, `RSK_BTC`, `USDT_ERC20`, `USDT_TRC20`, `USDT_LIQUID`, `USDT_LIGHTNING`, `SPARK`, and `STACKS`. Settlement support depends on the provider registered for each asset — see [Escrow Lifecycle](/guides/escrow-lifecycle).
