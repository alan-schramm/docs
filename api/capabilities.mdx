A capability grant is a participant's recorded consent to a specific class of protocol action — for example creating trade intents or releasing escrow. Grants are self-issued: you grant them to yourself, and they express your own consent, not independent authorization by a third party. Anything outside your granted scope is denied.

<Note>
  Production nodes always enforce capabilities. Before you create intents or move escrow funds, make sure your participant holds the canonical grants — the SDK's `capabilities.ensureCanonicalGrants(participantId)` does this idempotently.
</Note>

## Canonical capabilities

Only these (`capabilityName`, `scope`) pairs can be registered. Each scope is checked by a real gate in the node:

| `capabilityName` | Scopes | Gates |
| --- | --- | --- |
| `trade-coordination` | `intent.created`, `intent.discovering` | Creating an intent; proposing a trade for an intent |
| `settlement` | `settlement.escrow.released`, `settlement.escrow.refunded`, `settlement.escrow.split` | Releasing, refunding, or splitting escrow funds |

An unknown name, or a scope that belongs to a different capability, is rejected with `VALIDATION_ERROR`.

| Method | Path | Auth | Description |
| --- | --- | --- | --- |
| POST | `/v1/capabilities/register` | Session | Self-issue a grant |
| GET | `/v1/capabilities/:participantId` | — | A participant's live (non-revoked) grants |
| POST | `/v1/capabilities/:grantId/revoke` | Session | Revoke one of your grants |

## Register a grant

**`POST /v1/capabilities/register`**

<ParamField body="capabilityName" type="string" required>
  `trade-coordination` or `settlement`.
</ParamField>

<ParamField body="scope" type="string[]" required>
  One or more canonical scopes of that capability.
</ParamField>

<ParamField body="constraints" type="object">
  Optional constraints on the grant, for example `{ "expiresAt": "…" }`.
</ParamField>

```json Request
{
  "capabilityName": "settlement",
  "scope": ["settlement.escrow.released", "settlement.escrow.refunded", "settlement.escrow.split"]
}
```

```json Response (201)
{
  "success": true,
  "data": {
    "id": "…",
    "grantedTo": "5b1c…",
    "capabilityName": "settlement",
    "scope": ["settlement.escrow.released", "settlement.escrow.refunded", "settlement.escrow.split"],
    "constraints": null,
    "issuedBy": "5b1c…",
    "revokedAt": null,
    "createdAt": "2026-09-21T10:00:00.000Z"
  }
}
```

Registration is idempotent: if you already hold an equivalent live grant (same capability, covering the scopes, same constraints), that grant is returned instead of creating a duplicate — even under concurrent requests.

## List a participant's grants

**`GET /v1/capabilities/:participantId`**

Returns the participant's grants that haven't been revoked. No session required.

---

## Revoke a grant

**`POST /v1/capabilities/:grantId/revoke`**

Revokes one of your own grants immediately; actions that depend on it are denied from then on. Revocation has a stricter rate limit. To change a grant, revoke it and register a new one.

## Using the SDK

```typescript
// Idempotently self-issue both canonical grants (safe to run on every login).
await client.capabilities.ensureCanonicalGrants(participantId);

// Or manage grants yourself.
const grant = await client.capabilities.register({
  capabilityName: 'trade-coordination',
  scope: ['intent.created', 'intent.discovering'],
});
const grants = await client.capabilities.list(participantId);
await client.capabilities.revoke(grant.id);
```

<Warning>
  `capabilities.registerFromWallet()` is deprecated. It ignores the wallet's technical capabilities and simply self-issues the canonical grants — use `ensureCanonicalGrants()` instead.
</Warning>
