OpenSettlement moves the value of a trade. It locks the seller's asset in escrow, coordinates release to the buyer (or refund to the seller), and runs disputes when a trade breaks down. For client-held-key providers (`MULTISIG`, `LIGHTNING_HODL`, `SAFE_GUARD_EVM`), buyer and seller each hold their own key and sign independently — the node coordinates signature collection but can't move funds on its own.

Every endpoint on this page requires a session unless marked otherwise. Amounts are decimal strings.

## Escrow lifecycle

```text
CREATED → FUNDS_LOCKED → PAYMENT_PENDING → COMPLETED
               │                │
               │                └→ DISPUTED → COMPLETED | REFUNDED | SPLIT (by ruling)
               ├→ REFUNDED
               └→ EXPIRED (client-held-key providers: timelock passed before payment;
                           the seller recovers through arbitration)
```

| Method | Path | Who | Description |
| --- | --- | --- | --- |
| POST | `/v1/settlement/escrow` | Buyer or seller | Create an escrow for a trade |
| GET | `/v1/settlement/escrow/:id` | Party or assigned arbiter | Escrow detail |
| POST | `/v1/settlement/escrow/:id/submit-key` | Buyer or seller | Submit your client-generated escrow public key |
| POST | `/v1/settlement/escrow/:id/lock` | Seller | `CREATED → FUNDS_LOCKED` |
| POST | `/v1/settlement/escrow/:id/payment-sent` | Buyer | `FUNDS_LOCKED → PAYMENT_PENDING` |
| POST | `/v1/settlement/escrow/:id/release` | Party | Release (direct-call providers only) |
| POST | `/v1/settlement/escrow/:id/refund` | Party | Refund (direct-call providers only) |
| POST | `/v1/settlement/escrow/:id/initiate-release` | Party | Start a release signing round (client-held-key providers) |
| POST | `/v1/settlement/escrow/:id/initiate-refund` | Party | Start a refund signing round (client-held-key providers) |
| POST | `/v1/settlement/escrow/:id/submit-transaction-signature` | Required signer | Submit your signature for the round |
| GET | `/v1/settlement/escrow/:id/pending-transaction` | Party or assigned arbiter | The round in progress |
| POST | `/v1/settlement/escrow/:id/approve-release` | Buyer or seller | Two-person approval (when enabled) |
| GET | `/v1/settlement/escrow/:id/release-approvals` | Party or assigned arbiter | Recorded approvals |
| POST | `/v1/settlement/escrow/:id/dispute` | Party | Open a dispute |
| POST | `/v1/settlement/escrow/:id/initiate-expiry-recovery` | Seller | Recover an `EXPIRED` escrow through arbitration |

## Create an escrow

**`POST /v1/settlement/escrow`**

<ParamField body="tradeId" type="string" required>
  The trade this escrow secures. You must be its buyer or seller.
</ParamField>

<ParamField body="lockedAmount" type="string" required>
  Amount to lock, as a positive decimal string.
</ParamField>

<ParamField body="asset" type="string" required>
  Asset being locked (for example `BTC`, `USDT_ERC20`).
</ParamField>

<ParamField body="type" type="string">
  Provider: `MULTISIG`, `LIGHTNING_HODL`, `WDK_USDT_EVM`, `SAFE_GUARD_EVM`, or `MOCK`. If omitted, the node picks the implementation registered for the asset (`MOCK` only when the node runs in mock-escrow mode). `LIQUID_COVENANT` is reserved and not implemented.
</ParamField>

<ParamField body="network" type="string">
  Optional network override.
</ParamField>

<ParamField body="timelockHours" type="number">
  Optional timelock before an unpaid escrow can expire.
</ParamField>

Returns `201` with the escrow.

## Get an escrow

**`GET /v1/settlement/escrow/:id`**

Returns the escrow, its event history, and:

- `disputes` — any dispute on this trade. This is how the party who didn't open a dispute learns its ID.
- `custodyModel` — the provider's disclosed key-custody model, for example `client-held-buyer-seller-keys-server-held-arbiter` (`MULTISIG`, `LIGHTNING_HODL`), `client-held-buyer-seller-keys-server-held-kms-arbiter` (`SAFE_GUARD_EVM`), or `server-custodial-reference-implementation` (`WDK_USDT_EVM`). `null` for `MOCK`.
- `distributionPolicyFreezes` — for escrows with a protocol fee, the fee-distribution policy that was frozen when each fee collection was confirmed.

Returns `403` unless you are the buyer, the seller, or the dispute's assigned arbiter.

## Submit your escrow key

**`POST /v1/settlement/escrow/:id/submit-key`** — `MULTISIG`, `LIGHTNING_HODL`, `SAFE_GUARD_EVM`

Buyer and seller each submit their own public key, generated client-side with the SDK's `generateEscrowKeypair()`. Once both are in, the node derives the escrow's deposit address.

<ParamField body="pubkey" type="string" required>
  33-byte compressed secp256k1 public key, hex-encoded (starts with `02` or `03`). Never reuse your identity key.
</ParamField>

<ParamField body="capabilityProfile" type="string">
  Optional signer capability profile, for providers that check it.
</ParamField>

Returns `{ escrow, buyerKeySubmitted, sellerKeySubmitted }`. Idempotent per role.

## Lock, mark payment sent

**`POST /v1/settlement/escrow/:id/lock`** — seller only. Moves `CREATED → FUNDS_LOCKED` once the provider confirms the funds are locked.

**`POST /v1/settlement/escrow/:id/payment-sent`** — buyer only. Moves `FUNDS_LOCKED → PAYMENT_PENDING` after you've sent the off-chain payment (for example PIX). Share proof over the trade channel.

---

## Release and refund (direct-call providers)

**`POST /v1/settlement/escrow/:id/release`** and **`POST /v1/settlement/escrow/:id/refund`**

For `MOCK` and `WDK_USDT_EVM`. Release pays out to the **buyer's registered payout address** for the escrow's asset (see [Payout addresses](#payout-addresses)). A `toAddress` in the body is accepted for compatibility but ignored — the destination always comes from the registered address.

<Warning>
  `MULTISIG`, `LIGHTNING_HODL`, and `SAFE_GUARD_EVM` reject these routes. Their keys are client-held, so funds only move through the [signing round](#signing-rounds) with the required signatures.
</Warning>

## Signing rounds

For client-held-key providers, release and refund are two steps: build an unsigned transaction, then collect the required signatures.

### Start a round

**`POST /v1/settlement/escrow/:id/initiate-release`** and **`POST /v1/settlement/escrow/:id/initiate-refund`**

Builds the unsigned transaction and returns the pending transaction (`201`). It doesn't move funds or change the escrow's status. The release destination is the buyer's registered payout address, fixed when the round starts — a later change to that address doesn't affect a round already in progress. A `toAddress` in the body is ignored.

The response includes `kind`, `requiredSigners` (the participant IDs that must sign), and `unsignedPsbtBase64` — the payload to sign:

| Provider | Payload |
| --- | --- |
| `MULTISIG` | A PSBT (base64) |
| `LIGHTNING_HODL` | A JSON bundle of Ark transaction PSBTs |
| `SAFE_GUARD_EVM` | A JSON bundle with an ERC-4337 user operation and its `userOpHash` |

Only one round can be in flight per escrow. On a disputed release the arbiter's signature is already embedded, so only one party needs to sign.

### Submit your signature

**`POST /v1/settlement/escrow/:id/submit-transaction-signature`**

<ParamField body="signedPsbtBase64" type="string" required>
  Your signed copy of the payload: sign with `signEscrowPsbt()` (`MULTISIG`), `signEscrowArkTx()` (`LIGHTNING_HODL`), or `signEscrowSafeUserOp()` (`SAFE_GUARD_EVM`, a `0x`-prefixed 65-byte ECDSA signature — same field name).
</ParamField>

Returns `{ complete }`. `complete: true` means every required signer has submitted, the transaction was finalized and broadcast, and the escrow moved to `COMPLETED` or `REFUNDED` with a `txReleaseId`. `complete: false` means other signers are still pending. Returns `403` if you aren't a required signer.

### Read the round

**`GET /v1/settlement/escrow/:id/pending-transaction`** — returns the round in progress, or `404` if there is none.

## Two-person approval

**`POST /v1/settlement/escrow/:id/approve-release`** records your approval (buyer or seller only; idempotent) and returns `{ approval, readyToRelease }`. **`GET /v1/settlement/escrow/:id/release-approvals`** returns `{ approvals, readyToRelease }`. Approvals only gate releases when the node runs with dual-approval release enabled.

## Disputes

If a trade breaks down, either party can open a dispute. An arbiter is assigned, the parties submit evidence, and the arbiter issues a **signed** ruling that the node verifies before executing it. The node may also propose an automated ruling from on-device AI, which either party can reject during a contest window.

| Method | Path | Who |
| --- | --- | --- |
| POST | `/v1/settlement/escrow/:id/dispute` | Party |
| GET | `/v1/settlement/disputes` | Arbiter (your assigned disputes) |
| GET | `/v1/settlement/disputes/:id` | Party or assigned arbiter |
| POST | `/v1/settlement/disputes/:id/evidence` | Party |
| POST | `/v1/settlement/disputes/:id/contest` | Party |
| POST | `/v1/settlement/disputes/:id/resolve` | Assigned arbiter |
| POST | `/v1/settlement/disputes/:id/appeal` | Party |
| GET | `/v1/settlement/disputes/:id/semantic-record?appealRound=N` | Party |

Dispute statuses: `OPENED`, `EVIDENCE_SUBMITTED`, `AUTO_PROPOSED`, `ARBITRATED`, `RESOLVED`, `APPEALED`.

### Open a dispute

**`POST /v1/settlement/escrow/:id/dispute`**

<ParamField body="reason" type="string" required>
  Why you're disputing. Visible to the arbiter.
</ParamField>

<ParamField body="evidence" type="array">
  Optional initial evidence. Each item: `{ type, uri?, note?, evidenceReferenceId?, externalReference? }`. Use `evidenceReferenceId` to point at media stored through [Proof](/api/proof).
</ParamField>

Moves the escrow to `DISPUTED`, persists the dispute, and assigns an arbiter.

### Submit evidence

**`POST /v1/settlement/disputes/:id/evidence`**

Same item shape as above, plus an optional `idempotencyKey` (up to 200 characters) so a retry never records the same evidence twice. Allowed while the dispute is `OPENED` or `EVIDENCE_SUBMITTED`; moves it to `EVIDENCE_SUBMITTED`. If the node has automated resolution enabled, this can trigger an automated proposal — the response is always just the updated dispute.

### Contest an automated proposal

**`POST /v1/settlement/disputes/:id/contest`**

While a dispute is `AUTO_PROPOSED` and before its `autoResolutionDeadline`, either party can reject the proposal. The dispute returns to `EVIDENCE_SUBMITTED` and the already-assigned arbiter decides. After the deadline, returns `400`.

### Resolve (arbiter)

**`POST /v1/settlement/disputes/:id/resolve`**

<ParamField body="ruling" type="string" required>
  `RELEASE` (to the buyer), `REFUND` (to the seller), or `SPLIT`.
</ParamField>

<ParamField body="splitBuyerBps" type="integer">
  Required for `SPLIT`: the buyer's share in basis points (1–9999).
</ParamField>

<ParamField body="authoritySignature" type="string" required>
  Hex Ed25519 signature, by the arbiter's registered key, over the canonical ruling decision (dispute, escrow, appeal round, arbiter, ruling, split share, and `authorityIssuedAt`).
</ParamField>

<ParamField body="authorityIssuedAt" type="string" required>
  ISO timestamp included in the signed decision.
</ParamField>

The node verifies the signature against the arbiter's registered key before any settlement runs — a request without a valid signature is rejected with `403`. Payouts go to the parties' registered payout addresses; `releaseToAddress` and `refundToAddress` are accepted for compatibility but ignored. `SPLIT` is supported for `MOCK`, `WDK_USDT_EVM`, and `MULTISIG`.

<Tip>
  The SDK's `settlement.resolveDisputeWithWallet()` builds the canonical decision and asks your wallet to sign it, so you never assemble the signature by hand.
</Tip>

### Appeal

**`POST /v1/settlement/disputes/:id/appeal`**

Either party can reopen a `RESOLVED` dispute for a larger, reputation-weighted panel when the node runs market arbitration. Returns `{ dispute, appealFeeRequired }`; the appeal fee is refunded or forfeited once the panel rules.

### Semantic record

**`GET /v1/settlement/disputes/:id/semantic-record?appealRound=N`**

Returns the durable ruling record for a given appeal round. Only the trade's parties can read it.

### Recover an expired escrow

**`POST /v1/settlement/escrow/:id/initiate-expiry-recovery`**

If an escrow reached `EXPIRED` before payment, the seller — the only party with funds at stake — opens an arbitration to recover them. Returns the created dispute.

## Payout addresses

Every release, refund, and ruling pays out to the beneficiary's registered address for the escrow's asset. Register yours before you trade.

**`POST /v1/settlement/payout-addresses`**

<ParamField body="asset" type="string" required>
  The asset this address receives, for example `BTC`.
</ParamField>

<ParamField body="address" type="string" required>
  Your payout address for that asset.
</ParamField>

One address per `(participant, asset)`; registering again replaces it.

**`GET /v1/settlement/payout-addresses/:participantId/:asset`** — self only (`403` for anyone else). Returns `{ participantId, asset, address }`, or `404` if you haven't registered one.

## Payment accounts

A payment account is a hashed off-chain payment identity (for example a PIX key) that builds trust over time. Hash the raw identifier client-side with the SDK's `hashPaymentAccount()` — never send the raw value.

| Method | Path | Auth | Description |
| --- | --- | --- | --- |
| POST | `/v1/settlement/payment-accounts` | Session | Register `{ accountHash, paymentMethod }`. Idempotent for an existing hash. |
| GET | `/v1/settlement/payment-accounts/:accountHash` | — | Public trust view of an account (no owner identity) |
| POST | `/v1/settlement/payment-accounts/:accountHash/sign` | Session | Attest a completed trade with this account |

`paymentMethod` is one of `PIX`, `TED`, `BANK_TRANSFER`, `CRYPTO_DIRECT`, `LIGHTNING_DIRECT`, `CASH`, `OTHER`.

## Errors

| `error` | HTTP | When |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Missing field, invalid amount or key, `SPLIT` without `splitBuyerBps`, or a closed contest window |
| `AUTH_ERROR` | 401 | Missing or expired session |
| `FORBIDDEN` | 403 | Not a party, not the required signer, not the assigned arbiter, or an invalid ruling signature |
| `NOT_FOUND` | 404 | Escrow, dispute, round, profile, or payout address not found |
| `ESCROW_ERROR` | 409 | Action from an invalid state, a direct release on a client-held-key provider, a round already in flight, or no registered payout address |
| `RATE_LIMIT_EXCEEDED` | 429 | Too many requests (disputes, rulings, and appeals have a stricter limit) |
