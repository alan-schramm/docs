The Sails Protocol server exposes a versioned REST API at `/v1/*` alongside a WebSocket endpoint for real-time trade communication. Every request and response body uses JSON, and all application-facing interactions are organized around the Intent lifecycle — you express what you want to do, and the protocol coordinates the underlying modules on your behalf.

## Base URL

Point your client at the URL of your Sails node. For local development, the reference implementation runs at:

```
http://localhost:3000
```

<Note>
  In production, replace `http://localhost:3000` with the URL of your own Sails node. Sails Protocol is self-hosted — there is no shared cloud endpoint.
</Note>

The WebSocket endpoint is available at:

```
ws://localhost:3000/ws?userId=<your-participant-id>
```

## API Modules

All routes follow the convention `/v1/{module}/{resource}`. Each of the nine protocol modules has its own prefix:

| Module | Prefix | Description |
|---|---|---|
| OpenIdentity | `/v1/identity` | Register and authenticate participants |
| OpenLiquidity | `/v1/liquidity` | Publish and discover offers |
| OpenP2P | `/v1/openp2p` | Trades and negotiation |
| OpenSettlement | `/v1/settlement` | Escrow and disputes |
| OpenReputation | `/v1/reputation` | Trust scores and vouching |
| OpenAgents | `/v1/agents` | AI-assisted intent generation |
| OpenProof | `/v1/proof` | Cryptographic claims and evidence |
| Capabilities | `/v1/capabilities` | Capability grants (RFC-013) |
| Peers | `/v1/peers` | P2P transport management |

The Intent Engine (`/v1/intents`) sits outside the module convention deliberately — Intent is a cross-cutting Core primitive, not owned by any single module.

## Health Check

Before making any other requests, confirm your node is running:

```bash
GET /health
```

A healthy node responds with:

```json
{
  "status": "ok",
  "timestamp": "2025-01-15T10:00:00Z",
  "version": "0.1.1",
  "protocol": "Sails Protocol",
  "module": "Sails OpenP2P",
  "referenceImplementation": "Satsails Wallet",
  "features": {
    "mockEscrow": false,
    "mockSettlement": false
  }
}
```

You can also hit the root path for a quick overview of the node:

```bash
GET /
```

## Response Format

All responses are JSON. Successful responses return the requested resource or action result wrapped in a `data` envelope with a `success` flag — for example, a `POST /v1/identity/participants` call returns `{ "success": true, "data": { ...participant } }`.

Error responses always follow this shape:

```json
{
  "success": false,
  "error": "NOT_FOUND",
  "message": "Participant not found: part_abc123",
  "details": [],
  "requestId": "req-7f3a1c",
  "docsUrl": "https://github.com/alan-schramm/Sails-Protocol/blob/main/docs/API_REFERENCE.md#9-error-response-shape"
}
```

Every error response includes a `requestId` (matching the server log line for that request) and a `docsUrl` pointing to the error code reference. Use the `requestId` when reporting issues — it lets you pinpoint the exact failed request in server logs.

The full error code taxonomy:

| `error` | HTTP Status | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Request body or query failed schema validation |
| `NOT_FOUND` | 404 | The referenced resource does not exist |
| `AUTH_ERROR` | 401 | Missing or invalid session token |
| `FORBIDDEN` | 403 | Authenticated, but not authorized for this specific action |
| `ESCROW_ERROR` | 409 | An escrow action was attempted from an invalid state |
| `RATE_LIMIT_EXCEEDED` | 429 | Too many requests — check response headers for retry timing |
| `REQUEST_ERROR` | 4xx | Request rejected for a reason not covered above |
| `INTERNAL_ERROR` | 500 | Unexpected server error |

## Authentication

Most endpoints require an active session. Pass your session token in the `Authorization` header on every authenticated request:

```
Authorization: Bearer <your-session-token>
```

Sails Protocol uses Ed25519 challenge-response authentication — no passwords or API keys. You register a public key, sign a server-issued challenge, and receive a session token. See the [Authentication guide](/api/authentication) for the full step-by-step flow and SDK usage.

## API Versioning

The API is currently at `v0.1`. The stable contract guarantees no breaking changes to any documented endpoint until v1.0. All routes are prefixed with `/v1/` — when a future major version ships, `/v2/` routes will be introduced alongside the existing `/v1/` routes before the older version is retired.

  The Swagger UI is available at `/docs` on your Sails node for interactive exploration and live request testing against your local instance.
</Tip>
