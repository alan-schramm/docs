The trade channel at `/v1/openp2p/chat` carries real-time communication between the two parties of a trade: chat messages, trade and escrow status changes, presence, and risk warnings. You open one connection, then join each trade you want events for.

## Connecting

WebSocket upgrades can't carry an `Authorization` header, so the channel authenticates with a short-lived, single-use ticket:

<Steps>
  <Step title="Get a ticket">
    ```bash
    POST /v1/identity/ws-ticket
    Authorization: Bearer <sessionToken>
    ```

    ```json
    { "success": true, "data": { "ticket": "<64-char hex>", "expiresIn": 30 } }
    ```
  </Step>
  <Step title="Open the socket">
    ```javascript
    const ws = new WebSocket(`ws://localhost:3000/v1/openp2p/chat?ticket=${ticket}`);
    ```

    Use the ticket within `expiresIn` seconds (30 by default). It's consumed on first use — fetch a new one for every connection or reconnection. A missing, invalid, or reused ticket gets an `ERROR` frame and the socket closes.
  </Step>
  <Step title="Join a trade">
    ```json
    { "type": "JOIN_TRADE", "payload": { "tradeId": "…" } }
    ```

    Only the trade's buyer or seller can join it. One connection can join several trades; use `LEAVE_TRADE` to stop receiving events for one of them.
  </Step>
</Steps>

<Note>
  Messages are relayed and stored by the node you're connected to (message history is available at `GET /v1/openp2p/chat/:tradeId/messages`). Don't send secrets you wouldn't store with that node operator.
</Note>

## Client → server messages

Every frame is JSON with a `type` and a `payload`:

| Type | Payload | Description |
|---|---|---|
| `JOIN_TRADE` | `{ "tradeId": "…" }` | Subscribe to a trade's events. Required before sending or receiving for that trade. |
| `SEND_MESSAGE` | `{ "tradeId": "…", "content": "…", "msgType": "TEXT" }` | Send a message to your counterparty. `content` is 1–10,000 characters; `msgType` is `TEXT` (default), `IMAGE`, or `FILE`. Rate-limited per participant. |
| `LEAVE_TRADE` | `{ "tradeId": "…" }` | Unsubscribe from a trade without closing the connection. |
| `PING` | `{}` | Keep-alive. The server replies with `PONG`. |

## Server → client events

| Type | Description |
|---|---|
| `NEW_MESSAGE` | A chat message was sent in a trade you joined. |
| `TRADE_STATUS_UPDATE` | The trade's status changed. |
| `ESCROW_STATUS_UPDATE` | The escrow's status changed (for example `FUNDS_LOCKED`, `PAYMENT_PENDING`, `COMPLETED`). |
| `RISK_WARNING` | On-device AI flagged a message as a possible social-engineering pattern. Detection only — the trade is never blocked or changed. Off unless the node enables it. |
| `USER_ONLINE` | A party joined the trade channel. |
| `USER_OFFLINE` | A party left the trade channel. |
| `PONG` | Reply to `PING`. |
| `ERROR` | Your last frame couldn't be processed (for example a rate limit or an invalid payload). `payload.message` explains why. |

<Warning>
  Treat every `RISK_WARNING` seriously — for example a request to move the conversation elsewhere or a sudden change of payment details. The decision to continue is always yours.
</Warning>

## Using the SDK

`client.openp2p.chat(tradeId)` (also available as `client.trades.chat(tradeId)`) handles tickets, joining, and reconnection with backoff for you — a fresh ticket is fetched on every reconnect:

```typescript
const channel = client.openp2p.chat(tradeId);

channel.onMessage((msg) => {
  console.log(`${msg.senderId}: ${msg.content}`);
});

channel.onEvent((frame) => {
  if (frame.type === 'ESCROW_STATUS_UPDATE') console.log('Escrow:', frame.payload);
  if (frame.type === 'RISK_WARNING') console.warn('Risk warning:', frame.payload);
});

channel.onConnectionStateChange((state) => {
  // 'open' (also after each successful reconnect) | 'reconnecting' | 'closed'
  console.log('Connection:', state);
});

channel.send({ content: 'I have sent the payment.' });

channel.leave(); // stop receiving events for this trade
channel.close(); // close the connection
```

| Method | Description |
| --- | --- |
| `onMessage(handler)` | Called for every `NEW_MESSAGE`. |
| `onEvent(handler)` | Called for every server frame, including status, presence, and risk events. |
| `send({ content, msgType? })` | Send a message to the counterparty. |
| `onConnectionStateChange(handler)` | Receives `'open'`, `'reconnecting'`, or `'closed'`. `'closed'` means `close()` was called or reconnection gave up. |
| `leave()` | Send `LEAVE_TRADE`; the connection stays open. |
| `close()` | Close the connection and stop reconnecting. |

## Catching up after a disconnection

If your client was offline, fetch what you missed from the node's durable record instead of relying on the socket:

```bash
POST /v1/openp2p/trades/:id/reconcile
Authorization: Bearer <sessionToken>
Content-Type: application/json

{ "sinceMessageCreatedAt": "2026-09-21T10:15:00.000Z" }
```

```json
{
  "success": true,
  "data": {
    "tradeId": "…",
    "currentTradeStatus": "ACTIVE",
    "currentEscrowStatus": "PAYMENT_PENDING",
    "missedMessages": [
      { "id": "…", "senderId": "…", "content": "Payment sent", "msgType": "TEXT", "createdAt": "2026-09-21T10:16:02.000Z" }
    ]
  }
}
```

`missedMessages` holds up to 100 messages created after `sinceMessageCreatedAt`, oldest first. Omit the field to start from the beginning of the conversation. Only the trade's buyer or seller can call it. In the SDK, the same call is `client.openp2p.reconcileTrade(tradeId, sinceMessageCreatedAt)`.
